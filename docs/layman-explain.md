# layman-explain — 大白话解释

## 解决什么问题

模型经常一条回答里塞满技术细节：Docker 网络模式、WebSocket 通信、Benchmark 数据、十几个参数。信息都对，但用户听完只剩一个感觉——**"所以到底啥意思？"**

本技能把当前对话中的模型回答、技术分析、日志结果、方案设计重新翻译成直接、易懂、不绕弯的人话，重点回答四件事：

1. 现在到底是什么情况
2. 这意味着什么、对用户有什么影响
3. 哪些重要、哪些暂时不用管
4. 下一步最应该做什么

**大白话 ≠ 小白教程**：目标是降低理解成本，不是降低技术准确性。用户可能有较强技术背景，只是当前回答信息过载、概念混在一起。

## 触发条件

用户说"大白话说一下"、"简单说"、"所以到底啥意思"、"我有点蒙"、"直接告诉我现在什么情况"、"别讲那么复杂"、"你说人话"、"没看懂"、"到底是啥"等表达，**且指向已有内容**（刚才那条回答、刚讨论的方案、刚贴的日志或输出）时触发。

## 与 dual-layer-explanation 的分工

| 意图 | 触发技能 |
|------|----------|
| 嫌**刚才那条回答**复杂，要人话重译 | `layman-explain` |
| 想**学习一个新概念**（"给我讲讲 X"、"我想真正搞懂 X"） | `dual-layer-explanation` |
| 没指向任何已有内容、只是查事实（"X 是什么"） | 直接回答，不触发技能 |

边界规则只声明在 `layman-explain` 的 description 中，`dual-layer-explanation` 不做改动（单向引用）。

## 核心规则速览

- **先说结论，不铺垫**：第一段就是"简单说：……"，禁止"这个问题其实比较复杂""首先我们先了解一下"这类开头
- **重新翻译，不是删词**：提炼原回答的结论、状态、关心点、下一步，而不是把专业词换成白话再念一遍
- **优先解释关系，不是名词**：用户缺的通常不是定义，而是"A 和 B 什么关系 → 所以造成什么结果"
- **强制区分已发生/可能发生**："现在可以确定的是……"/"大概率是……"/"唯一还没确认的是……"，不为大白话牺牲准确性
- **排障必答影响范围**：涉及 rm/truncate/Docker prune/Git reset 等危险操作时，必须主动回答"刚才到底改了什么、有没有动别的东西"；没有执行上下文时不编造，用"从目前你给出的命令只能确认这些"兜底
- **默认不重新调查**：基于当前已有上下文解释，不为"大白话解释"额外搜索网页、调用工具、读文件或展开新调查；除非用户明确要求核实、已有信息明显不足、或存在明显事实冲突/高风险错误。已有信息得不出确定结论就直说"现在只能确定到这里，再往下就是猜了"
- **解释完成即停**：交付物是解释本身。用户接着说"那你帮我修"，退出解释角色按普通会话处理，不顺手干活
- **不引入新的理解负担**：原则上不引入用户原本不需要知道的新概念；解释 A 要先补 B、C、D 三个新术语，说明解释方式选错了。优先用用户已使用的术语和上下文里的对象解释；能直接说明关系，就不先补基础课

## 输出结构

按复杂度灵活选择，不机械套模板：

- **简单问题**：`简单说：` 一句话 + 最多 2～4 段必要解释
- **中等复杂**：一句话 / 现在到底是什么情况 / 对你来说意味着什么 / 你接下来怎么做
- **特别复杂**：再增加"不用管什么"（过滤噪声）、"还差什么没确认"

## 适用场景

| 场景 | 解释重点 |
|------|----------|
| 排障 / 日志 | 哪坏了、为什么、已经影响什么、没影响什么；用户要继续处理时给下一步最小动作（不是必须给一条命令） |
| 架构 / Agent / 系统设计 | 谁在控制谁、谁真正干活、文件在哪里、数据怎么走 |
| 多方案比较 | 先说"真正的区别其实只有两个……"，不列十几个维度 |
| 模型比较 | 谁适合想/干/前端/大规模改代码，结合用户工作流，不堆 Benchmark |
| 命令 / 配置解释 | 先说"这条命令实际上干了什么"，再讲参数，不逐字符讲解 |

## 硬性约束

- 技术术语（Docker、Gateway、API、Token 等）不强行翻译，但复杂关系必须翻成人话
- 类比只用于帮助理解复杂关系，之后必须回到真实技术对象，不整篇用房水管厨房替代技术事实
- 删除"总的来说、值得注意的是、具体来说"等填充词
- 用户明显困惑时不再增加信息量，改答"你只需要记住这一件事：……"
- 发现前面的模型回答有误时直接说明"前面那句话说得不准确"，不维护模型面子
- 行动建议是条件化的：问题本身含明确下一步、或用户明显在排障过程中，才给最小下一步；不为凑结构强凑操作，用户只问"刚才发生了什么"就解释清楚
- 行动建议最多 1～3 步，命令可直接复制，先说风险

## 依赖

无。纯指令型技能，任何环境可用。
