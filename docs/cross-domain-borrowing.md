# Cross-Domain Borrowing — 跨领域借解

## 一句话

本行业第一性原理想透了还是卡，就横向去别的领域找相通解法。剥术语把问题抽象成底层结构（底层结构/核心矛盾/普通解法失效原因），从历史案例和至少 3 个彼此远的领域找结构同构的解机制（每案例 5 点），选 3 种机制翻译成当前处境的方案，推荐 1 个低成本可逆实验先试。

## 设计理念

第一性原理是纵向回本质，跨领域借解是横向看别的领域。同样底层结构的问题，另一个行业可能早解决十几年了——灵光一闪来自远领域的结构同构。

核心是**结构同构**：你的问题和远领域问题底层结构相同，所以他们的解机制能迁移。

两种典型失败要防：①借表象不借机制（"丰田用看板我也挂板子"，没理解看板解决的是信息流滞后）；②抽象层不对（太抽象什么都迁移不了，太具体没远领域匹配）。所以最关键是**剥术语找到对的结构层**。

案例真实性是底线：通识案例用知识，非著名/含数据的联网核实，标注置信，绝不编造。

## 触发方式

说以下任意一句即可触发：

- "跨领域借解 / 别的行业怎么解决这个问题"
- "换个领域找灵感 / 其他行业有没有类似解法"
- "跨界借鉴 / 类比别的领域破局"
- "我的问题别的行业可能早解决了 / 换个赛道想想这个结构"
- "卡住了本行业解不了看看别的领域"

即使用户贴了卡住的问题说"帮我从别的领域找找思路"、"换个角度类比一下"，也应触发。

**关键区分**：回本行业本质重推 → first-principles；拆一个成品好在哪 → reverse-deconstruction；多视角对撞 → expert-panel；系统研究出报告 → enhanced-hv-analysis；横向去别的领域借 → 本技能。

## 工作流程

### 1. 剥术语，抽象到底层结构
找：底层结构（什么类型的问题）/ 核心矛盾（不可调的张力）/ 普通解法失效原因（揭示的结构约束）。抽象层自检：3+ 远领域能共享、机制又能落地。

### 2. 找远领域案例（历史 + ≥3 远领域）
距离把控：3 领域彼此远、远本行业，两域共享方法就换。每案例 5 点：它的問題 / 机制 / 与我的同构点（结构相同非表面像）/ 可迁移 / 失效条件。案例标置信（通识/已核实/推断），非著名的联网核实，无网标"未能联网核实"。

### 3. 选 3 机制翻译方案
选 3 种最值得借的机制（不是 3 个案例），各翻译成当前处境方案，标可组合的协同点，推荐 1 个低成本可逆实验先试。只搬机制不搬表象。

## 力度控制

- 默认：剥结构 + 历史+3 远领域（各 5 点）+ 3 机制翻译 + 1 先试实验
- `--quick`：3 领域各一句 + 3 机制一句话方案 + 1 实验
- `--deep`：每案例展开机制原理 + 失效条件详写，可加到 5 领域

## 与同类技能的区分

| 技能 | 做什么 | 何时用 |
|------|--------|--------|
| **cross-domain-borrowing** | 跨远领域借结构同构的解机制 | 本行业解不了，横向找灵感 |
| first-principles | 纵向回本行业本质重推 | 打破惯性从底层重构 |
| reverse-deconstruction | 拆一个具体成品为什么好 | 学单个作品 |
| expert-panel | 多视角对撞同一问题 | 多领域决策要专家组 |
| enhanced-hv-analysis | 系统研究出长报告 | 研究一个对象 |

## 依赖

- 联网搜索（核实非著名案例，可选）。无网时通识案例照用、非著名标"未能联网核实"。核心无依赖。
