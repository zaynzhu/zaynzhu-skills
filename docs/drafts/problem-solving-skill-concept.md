## 使用边界

本文保存前期共识，供后续分析完成后对照整合。它不是项目规则、执行授权或后续技能的输入要求；不自动加载进其他技能的工作流，不要求其他分析沿用这里的框架或结论。

后续整合时，分别保留原始需求、新发现和分歧，再根据证据修订。不要把本底稿中的建议误写为已经确认的硬性要求。

## 已确认的意图

- 技能服务于高能力模型的深度思考与攻坚，不绑定具体模型、供应商或运行环境。
- 适用场景是项目在需求、业务、技术选择或思考路径上遇到困难，需要理解问题、分析取舍并形成具体执行路线。
- 充分发挥模型能力是首要目标。节省稀缺额度是合理分工的收益，不能转化为限制研究、压缩思考或仓促交付。
- 模型可以读取相关材料、按需联网、重新定义问题、质疑初始方案，也可以亲自编写核心实现、原型和进行小范围验证。
- 亲自实现核心部分既能检验路径，也能降低不同能力执行者之间的理解偏差；不能预设高能力模型只负责文字规划。
- 后续可由其他执行者完成繁琐的实现工作。执行路线应让对方知道怎么推进、怎么验收，以及出现什么情况应停止并交回。
- 不假设充分规划能消除所有实现判断。实际执行中出现的新证据可能推翻原方案，应保留重新分析的入口。
- 当前仅形成体系，暂不创建、安装或发布正式技能。后续会使用其他技能夯实思路，最后结合各方结论。

## 初步体系建议，待后续检验

### 工作责任

定义问题 → 探索与判断 → 核心实现或最小验证 → 执行路线设计 → 偏差回流。

这些是责任范围，不是必须逐项执行的固定流程；允许跳转、反复和按任务规模合并。研究方法、方案数量和验证形式由问题决定，不机械规定思考轮数或每步确认。

### 思考与行动的边界

- 优先处理会改变方向或造成大量返工的不确定性。
- 进一步调查应能说明可能改变哪项决定，避免无关扩展。
- 是否亲自实现，以能否消除关键不确定性、传达核心设计为判断依据，不仅按代码行数判断。
- 结论区分事实、假设、建议和未验证内容，保留关键理由与证据。
- 局部验证通过只支持对应范围，不推导为整体业务或生产可行。
- 关键证据不足时，产出下一步验证路线，不伪装成完整可执行方案。

### 执行路线应传递的信息

目标、必要上下文、成立前提、关键取舍、具体动作、已有核心实现及其成熟度、验收标准、可自主调整范围、失败或停止条件、交回要求。

按风险决定细节：关键业务规则和接口应具体，重复实现不必逐行规定。近期阶段可执行，远期阶段根据已知证据展开，不为尚未成立的前提过度设计。

### 偏差处理建议

| 情况 | 建议动作 |
|------|----------|
| 局部实现错误，目标和关键前提仍成立 | 执行者在约定范围内修复并验证 |
| 信息、工具或数据缺失，无法验证 | 标记受阻，停止依赖该结果的部分 |
| 核心假设失效，或需要改变业务规则、架构边界、验收标准 | 停止受影响路线，带证据交回重新判断 |

交回材料包含预期、实际、复现证据、已尝试内容、受影响假设和需要重新决定的问题。不能为了通过而降低验收标准，也不应把每个普通实现问题都升级给高能力模型。

### 与现有交接技能的关系

新技能侧重形成有依据的判断和执行路线；`enhanced-handoff` 侧重传递已有结论、依据和状态。新技能应能独立产出接手材料，无需强制串联交接技能。

当前交接技能并非全面禁止联网或思考，但其围绕整理已有材料的约束，不适合作为攻坚阶段的默认边界。

### 工具与兼容性

根据问题使用文件读取、搜索、代码执行和验证能力，不强依赖特定工具名称。缺少工具时说明未验证范围及其影响。产物应让没有原始对话、没有安装此技能的执行者也能理解和使用。

## 后续需要夯实的问题

- 怎样判断关键不确定性已降低到足以交给其他执行者？
- 高能力模型应亲自实现哪些核心部分，怎样避免无限扩大实施范围？
- 怎样表达核心设计，才能实际降低能力差距带来的误解？
- 如何设置既能止损、又不会频繁中断的停止与升级条件？
- 核心实现、验证证据和执行路线如何组织，才能低成本维护？
- 如何用真实任务验证技能效果，而不是仅验证文档格式？

建议评价重点：更早识别错误前提、减少执行猜测和返工、在路线失效时及时停止。文档长度、方案数量和固定步骤完成率不作为主要成绩。
