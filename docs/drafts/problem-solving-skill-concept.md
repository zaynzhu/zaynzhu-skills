# 攻坚与执行设计：融合设计底稿

状态：用户已确认体系方向。本文综合初始分析、逐轮拷问与第一性原理推导；已据此完成 `skills/problem-solving/` 首版、合成情境对照与用户验收；本文件保留设计依据。

本文是设计依据，不是项目规则或实施授权。后续分析可以挑战它，不自动加载进其他技能工作流。已确认偏好与进一步推导、待验证效果在下文分别说明。

## 一、统一定位：把关键判断转化为可靠的后续行动

技能服务于项目在需求、业务、技术选择或思考路径上遇到困难的场景。用户明确调用后，高能力模型自主理解问题、研究取证、选择路径，必要时亲自实现核心并验证，再把结果转化为其他执行者能够理解、落实和检查的行动路线。

充分发挥判断能力是首要目标；节省额度来自合理分工，不能变成压缩研究或仓促交接。允许有依据地否定原需求、建议换目标，也允许判断任务暂时不适合交出。

综合后的核心判断是：分工边界应随不确定性和理解难度变化。高能力模型负责把最容易导致方向错误、理解偏差或昂贵返工的部分做实；后续执行者在明确目标、示例和验收要求支持下推进。这个分工原则有待实际任务检验，不意味着执行天然简单，也不保证所有任务都适合拆分。

## 二、从第一性原理推导分工与投入

### 分清四类信息

| 类别 | 本设计中的含义 |
|------|----------------|
| 基本事实 | 规划本身不保证实现正确；局部实验只支持对应条件；接手者没有原始对话时，需要足够的上下文才能理解任务 |
| 待检验假设 | 详细文档足以传递理解；核心部分一定需要大工程；高能力模型想清楚后，剩下都能机械执行 |
| 目标 | 改善关键判断，让项目可靠推进，减少理解偏差和返工 |
| 现实约束 | 高能力模型额度有限；不同执行者能力与工具不同；重大业务取舍和显著增加的投入由用户决定 |

由此得到两个判断依据：行动应能改善关键决定或降低执行错误；有限资源投入一处，就有放弃其他用途的代价。这些依据用于选择下一步，不用于编造精确收益或额度预测。

### 选择下一步的顺序

先确定需要消除的关键不确定性，再判断什么证据足以支持下一步决定，最后选择取得证据的行动。行动可以是读取材料、联网核实、比较方案、构造样例、编写核心代码或运行实验。

“最小行动”以证据足够为前提。需要跨模块交互才能验证的风险，不能以孤立函数跑通替代；能够通过局部实验回答的问题，也不应默认展开完整工程。

第一性原理在目标混乱、约束可疑或方案膨胀时显式使用；问题清楚时不强制输出分析模板，也不固定方案数量、思考轮次或探索方法。

## 三、给探索自由，以关键决定和投入边界收束

在授权范围内，模型可以读取相关代码和业务材料、联网、重新定义问题、质疑初始方案、写核心实现并进行必要验证。研究需要能说明可能改变哪项决定，不为证明自己思考充分而无限扩展。

开始实施前，简短说明关键疑点、拟采取的动作，以及什么结果意味着继续或改向。小范围工作可直接进行，不增加每步批准；发现工作显著扩大时，先检查是否存在更小且充分的验证方式。仍需较大工程，就暂停说明已确认内容、扩大原因、预期收益和替代路径，让用户选择。

代码行数、模块数量等只作为规模预警，不能替代价值判断；“这是核心”也不能成为无限实施的理由。

技术手段和可逆局部选择可以自主判断。目标优先级、重要业务承诺和重大成本取舍交给用户；等待期间只暂停依赖该决定的工作，继续独立且有价值的调查。沿用用户已表达的偏好，不反复询问。

## 四、亲自实现同时承担验证与传达两项责任

高能力模型亲自写代码有两种不同用途：检验路径是否成立，以及把容易误解的关键设计做成可参考的实物。后一项是降低能力差距带来的偏差的重要手段，但其实际效果仍需验证。

| 用途 | 交付要求 |
|------|----------|
| 验证原型 | 标明实验性质、验证条件、结果和未覆盖项，不默认进入正式产品 |
| 供接手者扩展的核心实现 | 按项目规范完成必要验证，给出边界和使用示例，明确尚未完成的工程工作 |

文字理由、关键实现、输入输出样例和验收证据可以共同传达设计，按任务需要选择。不能假设增加文档长度就能消除理解差距，也不能把原型通过推导为整体业务或生产可行。

若后续仍处处依赖困难判断，应明确说明暂不适合交接，提出缩小本轮目标、补一次验证或继续完成一段的选择。需要较大投入时由用户决定。

## 五、执行路线是一段有适用条件的行动安排

不要求一次规划整个项目。优先把近期关键阶段做到可执行，远期写清方向与依赖；确定性高时可以给完整路线。必须标出证据支持到哪里、从哪里开始可能不成立，以及哪些假设仍需验证。

路线应根据实际任务传递以下信息，不强制拆成固定数量的文档：

- 要实现的目标、成功标准及不可随意改变的业务要求。
- 关键选择的理由、成立前提，以及重新考虑它们的条件。
- 已有核心实现或原型、验证结果和证明范围。
- 首个可执行阶段的具体动作、前置条件和可观察验收结果。
- 可自主调整的范围、未知区域、失效信号及需要交回的情况。

关键业务含义和高风险接口写细，普通重复实现避免逐行规定。接手者应简短核对目标、约束、首个动作和验收方式；普通细节自行查证，涉及核心意图的歧义提出具体问题，不靠猜测补齐，也不要求用户逐项批准复述。

默认交付独立可读的材料和可转发启动指令，由用户选择执行者。对端无需安装该技能或拥有原始对话，也不假定相同工具环境。

## 六、把调整、未知、受阻与失效分开

执行可以偏离具体写法，只要目标、关键思路和验收要求仍一致。保留原决策理由，是为了支持判断而非禁止挑战；新证据可以推翻原路线。

| 实际状态 | 处理方式 |
|----------|----------|
| 局部错误或可逆实现调整，关键前提仍成立 | 执行者在约定范围内修复或调整并验证 |
| 存在核心意图歧义，或拟议调整可能影响关键思路与结果 | 提出具体问题，由用户决定是否调整或交回分析 |
| 到达已标注的未知区域，尚无证据否定核心前提 | 提示用户选择让当前执行者继续探索，或交回高能力模型 |
| 缺少信息、工具或数据，无法验证 | 标记受阻，停止依赖该结果的部分，不宣称路线失败或成功 |
| 核心假设已被推翻，或必须改变关键业务要求、架构边界或验收标准 | 停止受影响路线，带证据请求重新判断，不继续按失效路线实施 |

进入未知区域和发现方案错误是不同状态。用户可以选择由谁研究未知问题，但不能把明知失效的原路线当作可靠路线继续推进。

交回只需携带足以重启判断的信息：预期、实际、复现证据、已尝试内容、受影响的假设及需要决定的问题。避免每个普通错误都升级，也避免高能力模型重新调查全部上下文。

常规任务凭事先确定的验收标准和实际证据结束；核心业务规则、架构变化或重大偏离等高风险情况，按路线提前规定的条件交回审查。执行者不能自行免除检查或降低验收标准。

## 七、使用入口与现有技能的分工

仅在用户明确调用时启用，不自动识别模型能力，不为普通小修自动启动深度研究。用户可以直接描述困惑，无需先完成诊断。

支持三个自然入口：开始时不知道怎么做、已有方案但需要判断是否成立、执行受阻后需要重新分析。模型先利用可用上下文和项目材料，再询问只有用户能决定的信息。

本技能负责形成判断、必要实现和执行路线；现有 `enhanced-handoff` 负责传递已有结论、依据和工作状态。新技能可独立交付，不强制串联其他技能，也不自动调度执行者。

现有交接技能并非全面禁止联网或思考，但整理已有材料的约束不宜直接套用到攻坚阶段。第一性原理则作为按需使用的方法，不将另一技能的固定输出结构变成本技能的必经流程。

工具按任务选取，不绑定模型、供应商、运行环境或特定工具名。缺少必要能力时说明未验证部分及其影响，不假装取得证据。

后续评测重点应覆盖：

| 场景 | 要观察的行为 |
|------|--------------|
| 初始需求包含错误前提 | 能否识别并有依据地调整问题，而非直接规划实施 |
| 文字描述容易导致核心实现误解 | 核心示例、实现和验收能否帮助独立接手者正确推进 |
| 局部验证逐渐变成大工程 | 能否缩小验证，或及时停下说明投入变化 |
| 只有第一阶段有足够依据 | 能否准确标记未知区域，避免伪造后续确定性 |
| 执行出现不同类型的偏差 | 能否区分局部修复、受阻、未知和前提失效 |
| 工作难以拆分或缺少验证工具 | 能否如实说明局限，给出有用的下一步 |

效果评价看关键判断是否改善、独立接手是否减少猜测与返工、路线失效是否及时被发现，以及整体投入是否合理。有可靠用量数据时记录研究、执行和返工成本；没有时说明测量限制，不凭篇幅或主观感受宣称省额度。
