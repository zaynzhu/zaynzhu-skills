# problem-solving 使用说明

用于项目卡在需求、业务或技术判断时，让高能力模型研究问题、验证关键前提，必要时亲自写核心实现，再形成可接手的执行路线。仅明确调用时启用，不绑定具体模型或运行环境。

## 如何开始

选择你希望承担攻坚工作的模型，明确调用：

> 使用 problem-solving。项目想实现……，目前卡在……。请研究关键问题，必要时写核心并验证，给出其他执行者可以落实的路线。如果需要展开较大工程，先说明投入变化。

不需要先诊断问题，也可以直接说：

> 使用 problem-solving。这个需求我越想越乱，帮我判断真正的问题是什么。

> 使用 problem-solving。这里是原方案和实际结果，请判断哪些前提失效，并修订路线。

## 会得到什么

根据证据，可能得到推荐方案、核心实现及验证、首段可执行路线，或下一步验证方案。模型也可以建议放弃原需求或说明暂不适合交接，不保证每次都能给完整工程计划。

默认路线保存在任务已有文件或 `docs/plans/<任务名>.md`，只有聊天能力时直接在回复中给出。路线说明关键理由、已验证范围、第一步、验收、未知区域及偏差处理，并附可转发启动指令。由你选择执行者，不自动调度。

## 你需要决定什么

重要业务取舍、显著扩大工程投入，以及进入未知区域后由当前执行者探索还是交回分析。普通技术细节和局部可逆调整不逐项询问。

核心前提已被证据推翻时，先停止受影响路线，再重新判断。接手者不能降低验收标准来通过检查。

## 设计取舍

第一性原理用于分清事实、假设、目标和约束，按需展开。核心代码既可用于验证，也可降低接手者的误解；实验原型与可扩展实现会分别标注。

深度研究、交接文档长度和实际节省额度并非同一件事。技能当前为实验状态，真实项目及不同能力执行者之间的效果仍需验证。

## 文件与安装

- [主指令](../skills/problem-solving/SKILL.md)。
- [执行路线模板](../skills/problem-solving/references/execution-route.md)：可按任务裁剪。
- [环境说明](../skills/problem-solving/ENVIRONMENTS.md)：能力适配与验证边界。
- [评测说明](../skills/problem-solving/evals/README.md)与[情境用例](../skills/problem-solving/evals/evals.json)：维护使用，日常无需加载。

安装时将整个 `skills/problem-solving/` 复制到目标平台的技能目录，例如目标项目的 `.codex/skills/` 或 `.claude/skills/`。也可明确要求模型读取 SKILL.md；是否自动发现由平台决定。

与 `enhanced-handoff` 的分工：本技能负责形成判断和路线，后者负责已有结论及状态的传递，不要求同时安装。
