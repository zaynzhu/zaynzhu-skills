# Project Onboard

跨平台已有项目引导器。扫一个已有项目，基于证据同时生成 `CLAUDE.md` 和 `AGENTS.md`，让任意 agent 进来就能直接上手开发。

## 核心理念

内置 `init` 够用但太粗——它列技术栈、目录、大概怎么跑，基本是泛泛而谈。这个 skill 解决"粗"的根因：**每条写入的规则都要能追溯到项目实际文件**，不是凭空编。证据先行，规则后写。

两条铁律：

1. **基于证据而非想象**：每条规则都有文件系统来源。查不到就标"未发现"，保留 section 但不编内容。宁可写"未发现测试配置"，也不写"运行测试"这种没依据的话。
2. **只读不跑（A 档）**：只读文件系统 + 只读 git 元数据（如 `git remote get-url origin`、`git log --oneline -20`），不执行任何会改变项目状态、触发构建或联网的命令。原因：init 类技能不该有副作用，且跑命令在陌生项目里可能踩雷。

## Phase 1: 扫描取证

**目标**：收集所有证据，填进"证据账本"。这是整个 skill 的基石——后面所有规则都从这里来。

### Step 1: 排除目录

扫描全程忽略下列目录（既是噪音又可能爆 context）：

```
node_modules  .git  dist  build  out  vendor  .next  .nuxt  target
__pycache__  .venv  venv  env  .idea  .vscode  coverage  .cache
.turbo  .svelte-kit  .gradle  bin  obj
```

目录结构 section 里也不展示这些。

### Step 2: 配置证据扫描

按 `references/scan-checklist.md` 的清单逐项用 Glob/Grep/Read 查证。清单覆盖所有常见语言/框架的配置文件名，**不先识别技术栈**——扫到啥算啥，这样不会漏多语言 monorepo。

每查到一项就填进证据账本，格式见 `references/scan-checklist.md` 末尾。查不到的标 `未发现`，不跳过。

`git log --oneline -20` 和 `git remote get-url origin` 是弱证据：能跑就顺带看，参差就忽略，不阻塞。提交规范不依赖它们。**非 git 仓库时这些 git 查询全部跳过**（退出码非零即跳过，不报错），仓库 URL 和提交规范 section 标"未发现"。

### Step 3: 源码结构扫描（门面文件策略）

这是跟 init 粗版的核心差异——不只看配置，还要理解源码结构。用"门面文件策略"有节制地全量看，方法见 `references/scan-checklist.md` 的"源码扫描方法论"。要点：

1. **骨架**：Glob 拿排除后的目录树，限深 3 层
2. **门面文件**：每个含源码目录按优先级读——`index.*`/`__init__.py`/`mod.rs`/`lib.rs`/`main.go` 等门面文件读全文（通常 re-export 公共接口，读它就懂目录职责），无门面时读最大文件前 50 行
3. **入口深读**：从配置推断的关键入口完整读，顺 import 链走一层

护栏：门面文件读全文、非门面只读前 50 行、源码总读取软上限 40 个，超了按目录重要性截断并在账本标注"已截断"。

### Step 4: 展示证据账本

以表格展示所有证据，让用户过目。这是"基于证据"的可见保证——用户能看到每条规则从哪来。

---

## Phase 2: 现有文件分析

**仅当项目已存在 `CLAUDE.md` 或 `AGENTS.md` 时执行。** 两份都没有 → 直接进 Phase 3。

1. Read 现有的 `CLAUDE.md` / `AGENTS.md`
2. 把里面已有的规则当作**证据之一**吸收进账本（用户写过的规则优先级高于从配置推断的，别跟用户对着干）
3. 按 `references/existing-file-merge.md` 判断合并还是重写
4. 扫到 `.cursorrules` / `.windsurfrules` / `.coderc` 等其他 AI 规则文件：仅作扫描线索吸收，不动它们

---

## Phase 3: 交互确认

依次确认两件事：

### 3.1 合并/重写（仅已有文件时）

展示"现有内容 → 新增内容"对比，让用户选：
- **合并**（默认）：保留用户已有规则，补上缺失 section
- **整份重写**：以新内容替换

快路模式下默认合并，不问。规则见 `references/existing-file-merge.md`。

### 3.2 证据账本确认

展示账本表格，问用户有没有要补充或修正的证据点（比如某条命令实际不用了）。确认后进 Phase 4。

---

## Phase 4: 生成规则

按 11 个固定 section 顺序生成，写入 `CLAUDE.md` 和 `AGENTS.md`。**两份内容完全一致**——同一份工程规则写两遍，因为用户的 CLAUDE.md 已声明两者同等效力。每节的写作模板和示例见 `references/section-templates.md`。

| # | section | 写什么 |
|---|---------|--------|
| 1 | 项目定位 | 一句话项目是干嘛的 |
| 2 | 技术栈 | 语言、框架、运行时、包管理器 |
| 3 | 目录结构 | 关键目录职责（不照搬整棵 tree） |
| 4 | 开发命令 | 确切命令 + 各自作用 |
| 5 | 测试 | 怎么跑 + 测试在哪 + 框架 |
| 6 | 代码约定 | 缩进/分号/命名/语言规则 |
| 7 | 提交规范 | commit 风格 + 是否有 commitlint |
| 8 | 目录约定 | 生成物/第三方目录明示"别碰" |
| 9 | 环境变量 | 必需 env 清单 |
| 10 | 关键入口 | 入口文件 + 职责 |
| 11 | 给 agent 的工作指引 | 开工前先读啥、改完怎么自测、怎么提交 |

**第 11 个是核心差异点**——这是 init 粗版没有的，直接呼应"没法直接 vibe coding"的痛点：文件末尾给 agent 一段开工指引。

查不到证据的 section 写"未发现"，保留 section 不删——让用户看到哪些没扫到，而不是假装不存在。

文件末尾加同步提示：

```
<!-- 本文件与 CLAUDE.md / AGENTS.md 保持同步，修改任一份请同步另一份 -->
```

边界情况：

| 场景 | 处理 |
|------|------|
| 空项目（几乎没代码） | 照常生成，大部分 section 标"未发现"，给骨架 |
| 单文件脚本 | 简化结构，合并相近 section |
| Monorepo | 目录结构按子包分组，开发命令列根 + 主要子包 |
| 已有一份文件 | 走 Phase 2 合并流程 |

---

## Phase 5: 自审与同步检查

生成后逐项检查，每项标 ✅/❌：

1. **证据可追溯**：每条规则都能对应到账本里的证据。Grep 扫描有无凭空编的命令/约定
2. **两份一致**：`CLAUDE.md` 和 `AGENTS.md` 内容逐行一致（除文件名提示行）
3. **占位符扫描**：Grep 搜 `{{`、`TODO`、`FIXME`、`未发现` 之外的人为占位
4. **section 完整性**：11 个 section 都在，顺序正确
5. **同步提示行**：两份末尾都有同步提示
6. **未发现合理性**：标"未发现"的 section 确实没扫到对应文件，不是漏扫

展示自审结果表格。❌ 项修复后重新检查。通过后写入文件。

写入时：先确认目标目录可写；若已有文件且用户选了合并，保留已有内容、补上缺失 section，不覆盖用户写的东西。

## 快路模式

用户说"直接生成""不用确认""快速"时启用：
- 跳过 Phase 2 的合并询问（有文件默认合并）
- 跳过 Phase 3 的账本确认
- 扫完直接生成 + 自审 + 写入
- 自审 ❌ 项仍要修，这步不能跳

## 设计原则

1. **证据先行**：证据账本是唯一事实来源，规则只是账本的提炼。账本给用户看过，规则才落地。
2. **只读不跑**：init 类技能不该有副作用。只读文件 + git 元数据，不跑项目命令。
3. **两份一致**：CLAUDE.md 和 AGENTS.md 同等效力，内容就该一致，漂移交给 enhanced-neat-freak 收尾。
4. **未发现 ≠ 不存在**：查不到也要标出来，让用户知道覆盖盲区，不假装全知。
