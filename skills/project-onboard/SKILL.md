# Project Onboard

扫描已有项目，以可追溯证据生成或更新根目录 `CLAUDE.md` 和 `AGENTS.md`。共享规则写入受管区块，区块外保留平台专属规则。

## 核心约束

1. **证据先行**：每条生成规则都能追溯到项目文件或用户本轮确认。
2. **冲突显式化**：配置、现有规则和文档互相冲突时记录冲突，不静默选择。
3. **取证阶段只读**：只读文件和 git 元数据，不安装依赖、不联网、不运行项目命令。
4. **写入范围受限**：仅创建或修改目标项目根目录的 `CLAUDE.md`、`AGENTS.md`；其他文件只读。
5. **输出保持高信号**：缺失信息留在交付报告，不把大量“未发现”写进长期加载的规则文件。
6. **合并可重复**：再次运行只更新受管区块，区块外内容保持不变，第二次生成不应产生新 diff。

## 工作流程

### Phase 0：安全预检

1. 确认目标项目根目录，不把当前工作目录或父目录当作默认目标之外的写入范围。
2. 读取目标目录及其父级作用域内已生效的 `AGENTS.md`、`CLAUDE.md`；发现嵌套规则文件时只作证据，不自动改动。
3. 读取根目录 `CLAUDE.md`、`AGENTS.md` 和其他 AI 规则文件，判断是否已有受管区块。
4. 若是 git 仓库，读取 `git status --short`。无关未提交改动不阻塞，但不得修改或提交；目标规则文件有未提交改动时必须采用精准合并，整份重写需要用户明确确认。
5. 明确模式：
   - 默认模式：扫描后展示证据、冲突和拟议 diff，再写入。
   - 快路模式：用户说“直接生成”“不用确认”“快速”时跳过确认，但仍执行现有文件分析、冲突处理和全部自审。

### Phase 1：扫描取证

按 `references/scan-checklist.md` 执行：

1. 先做仓库级清单，发现 manifest、workspace、CI、格式化、测试和 AI 规则文件。
2. 再按已发现的生态读取相关配置，不逐一加载无关语言的配置。
3. 生成限深目录骨架，识别 workspace 根和关键源码目录。
4. 按门面文件策略读取源码：入口完整读，直接 import 链走一层；源码总读取软上限 40 个文件。
5. 建立证据账本，记录维度、来源、摘要、可信度和冲突。

使用当前环境可用的只读工具完成检索：有 shell 时优先 `rg --files`、`rg -n` 和安全的文件读取；没有 shell 时使用等价的 Glob/Grep/Read 能力。不要把特定工具名当作运行前提。

#### 敏感信息护栏

- 不读取真实 `.env`、私钥、证书、凭据文件、认证缓存或系统 keychain。
- `.env.example`、`.env.sample`、`.env.template` 只提取变量名和注释，不展示示例值。
- 对 `application*.yml`、`config.toml` 等配置，优先提取 `${ENV_NAME}` 引用和键路径；发现疑似口令、token、连接串或用户信息时仅记录键名并标记“已脱敏”。
- 不查询或展示 `git remote` URL；仓库地址不是生成规则所需证据。
- 证据账本和最终回复都不得包含原始秘密值。

#### 证据可信度

| 级别 | 来源 | 用法 |
|------|------|------|
| 已确认 | 用户本轮明确说明 | 可直接写入 |
| 强事实 | manifest、lockfile、工具配置、CI | 可直接写入，但与现有规则冲突时先展示 |
| 强意图 | 当前作用域内现有 AI 规则 | 保留；与强事实冲突时标记冲突 |
| 弱证据 | README、源码风格抽样、git log | 只能描述为观察结果，不升级成强制规则 |

现有规则与当前配置冲突时，不自动认定任一方过期。默认模式让用户裁决；快路模式保留已有文字、从共享受管区块省略冲突项，并在交付报告列出。

### Phase 2：分析现有规则

按 `references/existing-file-merge.md` 处理：

1. 分别识别两份文件的共享规则、平台专属规则、自定义内容和受管区块。
2. 已有受管区块时只更新区块内部。
3. 没有受管区块时，把可确认的共享规则纳入新受管区块；保留自定义和平台专属内容。
4. 两份文件内容不同不代表错误，只要求共享受管区块一致。
5. 整份重写只在用户明确要求时执行。

### Phase 3：确认或应用默认策略

默认模式展示：

- 精简证据账本
- 未解决冲突
- `CLAUDE.md`、`AGENTS.md` 的拟议变更摘要或 diff
- 合并与整份重写的影响

快路模式直接采用以下安全默认值：

- 合并，不整份重写
- 保留区块外内容
- 不把未解决冲突写进共享区块
- 不触碰目标文件之外的未提交改动

### Phase 4：生成规则

使用 `references/section-templates.md` 生成共享受管区块：

```markdown
<!-- project-onboard:begin -->
<!-- 此区块由 project-onboard 维护；区块外可保留平台专属规则 -->

## 项目定位

...

<!-- project-onboard:end -->
```

按需使用以下推荐顺序，不强制生成空 section：

1. 项目定位
2. 技术栈
3. 目录结构
4. 开发命令
5. 测试
6. 代码约定
7. 提交规范
8. 目录约定
9. 环境变量
10. 关键入口
11. 给 agent 的工作指引

仅写入已确认或有明确证据的内容。单文件项目可合并相近 section；monorepo 按 workspace 分组。声明式命令可以记录，但必须在交付报告注明“未实际执行”。

新文件使用一个简短一级标题加受管区块。已有文件保留原一级标题和区块外内容。两份文件只同步受管区块，不强制整份逐行一致。

### Phase 5：自审与写入

先生成草稿并检查，再写入：

1. **可追溯性**：每条共享规则都能对应证据账本。
2. **冲突安全**：未裁决冲突没有被伪装成确定规则。
3. **受管区块一致**：两份文件中的 `project-onboard` 区块逐行一致。
4. **区块外保留**：现有平台专属和自定义内容未丢失。
5. **高信号**：受管区块不包含 `未发现`、`TODO`、`FIXME` 或模板占位符。
6. **脱敏**：输出不包含疑似秘密值、真实 `.env` 内容或 remote URL。
7. **写入范围**：diff 只涉及获准修改的两份规则文件。
8. **幂等性**：用同一证据再次生成草稿，结果不产生新 diff。

发现失败项先修正草稿，再写入。写入后重新读取两份文件并复核受管区块；不要运行项目测试、构建、安装或格式化命令。

## 交付

报告：

- 创建或更新了哪些规则文件
- 采用合并还是重写
- 受管区块包含哪些已验证维度
- 哪些信息未发现、哪些冲突仍待确认
- 哪些命令仅从配置读取、没有实际执行
- 是否通过受管区块一致性、脱敏和幂等性检查
