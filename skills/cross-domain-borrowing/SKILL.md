# 跨领域借解 — Cross-Domain Borrowing

## 设计理念

如果说第一性原理是**纵向**回到本质，跨领域借解就是**横向**看别的领域里相通的解法。你的问题在本行业用第一性原理想透了还是卡，往往不是你没想到，而是本行业的解法空间就那么大——但同样底层结构的问题，另一个行业可能早被解决十几年了。

核心信念：**灵光一闪往往来自远领域的结构同构。** 你和那个领域遇到的是同一个底层问题，只是裹了不同行业术语，所以他们的成熟机制能迁移给你。

跨领域借解的本质是**结构同构**：你的问题和远领域的问题在底层结构上同构（同样的矛盾、同样的约束形状），所以那个领域的解法机制能迁移。

两种典型失败，本技能要主动防：
1. **借表象不借机制**："丰田用看板，我也挂个板子"——没理解看板解决的是"信息流滞后"这个结构，不是板子本身。借的是机制，不是样子。
2. **抽象层不对**：太抽象（万物都是资源分配）→什么都匹配但什么都迁移不了；太具体→没远领域匹配。要找到那个"3+ 远领域能共享、又具体到机制能落地"的中间层。

所以最关键的一步是**剥行业术语，找到对的结构层**。这一步错了，后面全是硬凑。

案例真实性是底线：跨领域类比最易出幻觉——编一个听起来很像、其实不存在的案例，借解就建在沙上。通识案例用模型知识即可，非著名或含具体数据/年代的案例联网核实，输出里标注哪些是通识、哪些已核实、哪些是推断。

## 工作流程

### 准备：拿到困惑

从用户输入提取：**背景、当前做法、现实约束、具体卡点**。

如果信息不足以抽象出底层结构，用最合理的假设填上并标注，不反问把活推回用户。卡点说得太泛（如"增长卡住了"）时，不反问，用最合理的具体理解开始并在开头点明。

### 第一步：剥术语，抽象到底层结构

把问题剥掉行业术语，抽象成"人类在其他领域也可能遇到的"问题。找出三样：

1. **底层结构**：剥到什么类型的问题？（资源在约束下分配？信息滞后下的协调？局部最优 vs 全局最优？信任建立？规模化的瓶颈？）——这一层是远领域能共享的。
2. **真正的核心矛盾**：不是表面卡点，是结构里那个不可调和的张力（如"要快就要多存货，要省就不能多存货"）。
3. **普通解法失效的原因**：本行业那些显而易见的解法为什么不管用？——这揭示了一个结构约束，借来的机制必须正面解决它，否则白借。

**抽象层自检**：在这个抽象层下，能不能找到 3+ 个远领域共享它？共享不了说明太具体，往上抽象；万物都共享说明太抽象，往下收。找到那个"恰好 3+ 远领域能共享、机制又能落地"的层。

### 第二步：找远领域案例（历史 + 至少 3 个远领域）

从两类来源找结构同构的案例：
- **历史案例**：跨时间找（本行业或别的领域过去怎么解过同类结构问题）
- **至少 3 个彼此距离较远的领域**：跨领域空间找

**距离把控（重要）**：3 个领域要**彼此远、也远离用户本行业**。距离越远，借出来的越可能是灵光一闪（近领域借的是常识，远领域才出意外）。测试：如果两个领域共享同一套方法或词汇，换掉一个。目标是"最大化领域距离 + 最大化结构同构"——远到意外，又同构到能迁移。

**每个案例说明 5 点**：
1. 那个领域遇到了什么问题（它的具体形态）
2. 用了什么解决机制（机制本身，不是表象）
3. 与我的问题相似在哪里（结构同构点——是哪个结构相同，不是表面像）
4. 哪些部分可以迁移（机制里能搬过来的那部分）
5. 什么条件下会失效（机制的边界——超出什么条件就不灵了）

**案例真实性纪律**：
- 通识案例（丰田看板、免疫系统分布式防御、蜂群觅食等广为人知的）用模型知识即可
- **非著名、或含具体数据/年代/人名的案例联网核实**，别凭印象编
- 输出里标注每条案例的置信度：`[通识]` / `[已核实，来源+日期]` / `[推断]`
- 拿不准的明确标"暂未核实"，绝不编造案例
- **无联网工具时**：通识案例照用，本该核实的非著名案例标"未能联网核实"，继续借解不中断——诚实降级，不拿未核实当已核实

### 第三步：选 3 种机制，翻译成方案

从所有案例里选**最值得借的 3 种机制**（不是 3 个案例——是 3 种机制；一个案例可能含多种，也可能多个案例同一种）。

把每种机制翻译成适合用户当前处境的方案：
- **3 个独立翻译方案**：一种机制一个方案，保留机制→方案的映射（让用户看清哪个机制变成什么样、能挑能组合）
- **标出可组合的协同点**：哪几个机制能 1+1>2（如一个降延迟、一个分担风险，组合更稳）
- **推荐 1 个低成本可逆实验**：从 3 个方案里挑最值得先试的，设计成一个低成本、可逆的小实验（能快速验证借来的机制在当前处境是否真管用，失败了能退回）

翻译时只搬机制不搬表象：方案要像"你这个行业里的人会做的事"，但底层跑的是借来的机制。

## 边界说明

**不要做的事：**
- 不要借表象不借机制。"X 用了 Y，我也弄个 Y"——要讲清 Y 解决的结构是什么，否则是照猫画虎。
- 不要找 3 个近领域。近领域借的是常识不是灵光；3 个领域要彼此远、也远本行业。
- 不要硬凑结构同构。如果某领域只是表面像、结构不同，不要硬说能迁移——同构点是结构相同，不是表面像。
- 不要在抽象层不到位时就开始借。太抽象什么都迁移不了，太具体没远领域匹配，先调到对的层。
- 不要编造案例。非著名/含数据的案例联网核实，拿不准标"暂未核实"。
- 不要借了机制却不管失效条件。每个机制都有边界，超出条件就不灵，要写清。

**要做的事：**
- 剥术语是第一关键步——底层结构对了后面才有意义，错了全是硬凑。
- 普通解法失效原因要挖到结构约束，借来的机制必须正面解决它。
- 每个案例的"相似点"要落到结构同构，不是表面像。
- 案例标置信（通识/已核实/推断），非著名的核实。
- 翻译方案只搬机制不搬表象，方案要像本行业会做的事、底层跑借来的机制。
- 先试实验要低成本、可逆，能快速验证机制是否真管用。

## 力度控制

**默认行为**：剥结构 + 历史+3 远领域案例（各 5 点）+ 3 机制翻译 + 1 先试实验，最大扩散。

用户可在请求中调整：
- `--quick`：3 远领域各压缩成一句 + 3 机制一句话方案 + 1 实验（快速找灵感）
- `--deep`：每个领域案例展开机制原理 + 失效条件详写，可加到 5 个领域（吃透一个复杂卡点）
- 用户直接描述（如"快速给个灵感"、"这个卡点很重要深挖"）同样生效

## 与其他技能的区分

- **first-principles**：纵向回到本行业本质重新推导。本技能是**横向去别的领域借**——纵向想透了还卡，才轮到横向。
- **reverse-deconstruction**：拆一个具体成品为什么好、怎么用上。本技能是**跨多个远领域借解机制**，不是学单个成品。
- **expert-panel**：组互补专家组对撞同一问题。本技能是**跨领域结构同构借机制**，不是多视角辩论。
- **enhanced-hv-analysis**：系统研究一个对象的发展史+竞争格局。本技能是**对一个卡点做横向借解**，不出长报告。
- 当用户要"回本行业本质重推" → first-principles；"学一个成品好在哪" → reverse-deconstruction；"多视角对撞" → expert-panel；"系统研究出报告" → enhanced-hv-analysis；"本行业解不了，去别的领域借" → 本技能。
