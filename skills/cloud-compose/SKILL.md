# 云端构建与 Compose 交付

将项目变成可追溯、可导入、可启动的容器交付物。默认走 **GitHub Actions → 单架构镜像 tar → Compose 离线部署包**，目标机器只负责导入和运行。同时支持“镜像仓库 + Compose”。已有偏好时沿用；偏好未知且交付渠道会影响方案时给用户这两个选项，不阻塞与渠道无关的侦察和文件准备。用户未选择时默认离线 tar；明确要求两种才同时生成。

“快速”意味着复用已有配置、最少必要询问、优先构建目标架构，不意味着跳过运行验收。不能保证所有项目都能容器化；无法完成时，也要交付依据、已经可用的部分和下一条具体路径。

## 执行边界

- **默认严格云端**：允许本地读写文件、Git、调用远端工具和下载产物；依赖安装、编译、Docker/Podman 构建、镜像加载、Compose 校验和烟测都在云端执行。不要探测、安装或启动本地 Docker，也不要用本地 VM、容器或本机 self-hosted runner 绕过限制。仅有静态文本检查不等于 Compose 验证。
- 用户在当前任务中明确说“用本地 Docker/本地环境构建”才启用本地路径；“本地有 Docker”“随便怎么做”“云端失败”都不算。即便授权本地也先核实工具和目标架构，安装组件或启动守护进程另按实际授权处理。远端 Docker context 只有明确验证远端主机身份后才属于云端。
- 生成 Dockerfile、Compose 和 CI 不等于已经构建。构建成功不等于运行成功。按最后的状态表如实交付，不编造 run URL、镜像 digest 或验证日志。
- 复用本次会话已有授权，不重复问。按请求授权范围推进云端构建；上传未公开源码到新服务、改仓库可见性、发布公开镜像、开通付费资源和生产部署不从“打包”推导。先完成可审阅文件和差异，确有未授权外部动作时才针对那一步询问。
- 构建/烟测不使用生产数据库、生产凭据或真实第三方副作用；关闭调度、通知、收费调用和自动抓取。需要依赖时使用临时服务与测试数据。不要复制用户的 `.env` 到 CI 或打包产物。

## 1. 侦察并确定最小方案

先读目标项目就近 `AGENTS.md` / `CLAUDE.md`，检查 Git 状态与现有容器、CI、部署说明；不要覆盖未提交修改或启动未知脚本。用文件证据回答：

| 必须识别 | 证据和决策 |
|---|---|
| 构建与运行 | 清单、锁文件、运行版本、入口、端口、编译产物、健康接口；区分 Web、worker、一次性 CLI、纯库、桌面客户端 |
| 服务边界 | 应用服务、数据库/缓存、外部依赖、迁移任务；不照抄来源项目的两个容器结构 |
| 状态与配置 | 数据目录、UID/GID、运行时变量、前端构建时变量、密钥、首次初始化与升级步骤 |
| 目标环境 | 目标 OS/CPU、NAS/服务器的 Compose 能力、网络和资源；构建机架构不是目标架构 |
| 云端能力 | 现有远端及 CI、已登录工具、读取/提交/运行/下载权限、源代码所在 ref 与 commit；不打印 token |

输出一句方案和验收标准。已有证据就直接用，只问会改变方案的缺失信息。缺少路径且当前目录没有项目时询问路径；缺少目标架构时先完成通用文件，构建前询问或将默认架构明确标为待确认，不能称其为已适配目标。

按 [`references/project-adaptation.md`](references/project-adaptation.md) 处理不同技术栈。若项目本质不支持目标容器平台，解释具体阻塞并提出拆出后端、原生云端构建或远程服务方案，不生成没有实际用途的空容器来假装完成。

## 2. 生成最小交付文件

优先修补现有文件，不并行另造部署体系。至少覆盖：

1. **Dockerfile / .dockerignore**：按锁文件安装、构建阶段与运行阶段分离、只复制必需产物；工作区依赖和生成代码不能遗漏。排除凭据、数据库转储、缓存与无关大文件。避免无脑 `COPY . .` 带入运行数据；所需非敏感示例不要误排除。
2. **部署 Compose**：只引用本次镜像 `image:`，不含 `build:`、源码挂载或启动时编译/下载依赖；镜像 tag、服务、平台与包内清单一致。补齐健康检查、持久化、端口、网络、依赖就绪、重启策略。一次性任务与长驻服务分别验收。
3. **配置示例与说明**：Compose 插值文件和容器 `env_file` 分开说明；不填真实值，不覆盖目标机现有配置。为秘密使用必填校验而非可上线的默认密码；首次生成的配置权限为 `0600`。说明目录权限、数据库初始化/迁移、备份、升级与回滚限制。
4. **云端 workflow 和打包脚本**：遵循 [`references/cloud-workflow.md`](references/cloud-workflow.md)，默认手动触发并构建一个已确认架构。不要把全部语言、架构和云厂商硬塞进通用脚本。

镜像命名包含项目、服务、版本或 commit 标识，不只用 `latest`。所有用户输入（版本、平台、路径）先校验，GitHub 表达式通过 `env` 传给 shell 并引用变量，不能直接插进 shell 程序。拒绝路径穿越、选项注入和不合法 tag。

## 3. 在云端构建与验证

在本机通过 CLI/API 触发远端任务是允许的；所有 Docker 命令都明确标注运行位置，默认仅在云端 runner 执行。先确认待构建修改已在目标 ref，记录 commit SHA。GitHub workflow 首次手动触发不可用时检查默认分支是否已有 workflow；不得为让按钮出现而擅自合并或覆盖默认分支。

按既有授权提交/推送并启动任务；无权限也继续完成文件，交付精确到仓库、ref、workflow、输入的手动触发步骤。轮询同一服务间隔至少 2 秒，常规状态轮询建议 10–30 秒，重试有上限、退避并遵守服务的 Retry-After，不靠无限重跑掩盖失败。

依次验证：

- 用无敏感值的临时配置执行 `docker compose config --quiet`；确认配置只引用预构建镜像。检查必需文件路径和所用 Compose 功能，不把解析通过当运行通过。
- **离线包路径**：Buildx 构建目标平台，单平台 `--load` 后用 `docker save` 导出 Docker 可加载归档，不用 `docker export` 冒充镜像。多个架构各自出 tar、Compose/配置和清单；不要假定多平台 manifest 能直接按同一 `--load` 流程导出。
- 用本次交付 Compose，在云端隔离目录/项目名启动临时依赖，按真实入口验证就绪和至少一条关键功能路径；例如前端 → 反向代理 → API，或 CLI/worker 的可观察结果。数据库迁移单独验收，不连接生产库。设超时；失败保留脱敏日志并清理本次临时资源，绝不对生产环境执行 `down -v`。
- **离线包路径**：在干净的第二个云端 job 或等效干净镜像存储中下载部署包、校验 SHA256、`docker load`，断网或禁止拉取与构建，验证包内 Compose 能启动所需服务。包自包含时所有运行镜像（包括数据库、缓存、初始化容器、启用 profile 的依赖）都必须入包；若外部 DB/API 仍必需，明确叫“镜像离线包”，不要宣称完全离线可运行。
- **镜像仓库路径**：在干净云端 job 中登录目标仓库，按本次 digest 拉取，使用部署 Compose 验证关键路径；不要求生成 tar 或使用 `--pull never` 证明离线。交付镜像地址/digest、Compose、配置示例、清单与说明。
- 检查最终产物中没有密钥、真实 `.env` 或数据库数据；记录每个镜像实际 OS/架构、tag、image ID（仓库模式记录 registry digest），文件校验和、源码 commit、workflow run 和验收结果。首次上传的待验收 artifact 不算发布成功；验证 job 通过后再生成带结果的最终包及校验和，或单独附最终验证报告。最终报告必须关联已验收包的校验和，不能用新构建替换经过验收的镜像。校验和只证明完整性，不冒充来源签名。

若架构仿真、GPU、特定 NAS 或外部服务无法烟测，标明已验证平台和未验证项。只有所有选定服务成功才标记整包成功；服务部分成功不能掩盖其他失败。

## 4. 收集产物并交付

以下是默认离线包目录；镜像仓库路径省略 `images.tar`，将镜像地址/digest 写入清单，并按仓库拉取路径给部署命令：

```text
<project>-<version>-<platform>/
  images.tar
  SHA256SUMS
  compose.yaml
  compose.env.example
  app.env.example           # 按实际服务拆分，无此配置则省略
  manifest.json
  README.md
```

清单包含实际文件列表、源码 commit、云端 run 链接、各服务镜像/tag/ID/架构和验证范围。SHA256SUMS 覆盖 tar、Compose、示例、说明和清单，不包括校验文件本身；打包完成后再算。声明 artifact 保留期限，提供下载位置；用户要求长期发布且已授权时才上传 Release/其他持久存储。

README 给出在**目标部署机**执行的校验、导入、准备配置、初始化、`docker compose up -d --pull never --no-build`、健康检查及保留数据的升级/回滚命令。这些部署命令不是允许智能体在用户本机运行的授权。需要联网依赖时列清楚，严格离线场景不得静默改用仓库拉取。

最终简洁报告：文件位置、commit、云端 run/下载链接（有则给）、目标平台、构建/校验/烟测各自结果、未完成项及下一步。

| 状态 | 可声称的结果 |
|---|---|
| 已生成 | 文件已完成，尚无云端运行证据 |
| 已构建 | 镜像与产物已生成，但运行验收不完整 |
| 已验证 | 云端构建、所选渠道的导入/拉取、所声明范围的运行验收通过；不等于生产已部署 |
| 受阻 / 部分完成 | 指明失败步骤、证据、可用文件、替代方案和解锁动作 |

## 5. 遇到阻塞也要推进

使用 [`references/fallbacks.md`](references/fallbacks.md)，每次给出“具体原因 → 已尝试及结果 → 首选解法 → 备选解法 → 需要用户做的一步”。能在既有授权内修复就修复后重跑；不要只丢下一句“请安装 Docker”。不因云端失败自动回退本地，不自动新开收费服务，不重复询问已知条件。
