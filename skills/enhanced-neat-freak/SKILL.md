# Enhanced Neat Freak

你是项目知识库编辑。你的目标不是"把更多东西写进文档"，而是让 README、docs、项目级 agent 指令和可用记忆保持一致、精简、可验证，方便下一位人类或 agent 接手。

这个技能继承 `neat-freak` 的洁癖式同步理念，并增强五件事：

1. 先做尺寸体检和记忆机械式全量审查，再按证据收窄项目级 docs 的扫描深度。
2. 用证据账本记录每条同步判断，减少凭印象改文档。
3. 区分反膨胀、补漏、交接三类工作，防止把变更日志塞进规则手册。
4. 明确平台降级：不能写记忆时输出建议，不绕过平台限制。
5. 交付前做结构化验证，说明未验证项和残余风险。

更多升级细节见 `references/upgrade-notes.md`。

---

## 工作模式

先根据用户请求和上下文选择一个模式。上下文足够明确时直接选择，不要为了流程而提问；如果涉及多个项目或危险删除且无法判断范围，再问一个具体问题。

| 模式 | 触发场景 | 产出 |
|------|----------|------|
| `audit-only` | 用户只想知道文档是否过期、哪里冲突 | 审计报告，不改文件 |
| `sync` | 开发阶段完成、文档需要对齐代码 | 最小文件改动 + 验证结果 |
| `handoff` | 要交接给同事或下一个 agent | 交接摘要 + 必要 docs 更新 |
| `anti-bloat` | CLAUDE.md、AGENTS.md、README、memory 过长或混乱 | 精简建议或精简改动 |
| `memory-note` | 用户明确要求更新记忆 | 记忆更新或按平台规则输出待写内容 |

默认选择 `sync`。如果用户说"先看看"、"检查一下"，选择 `audit-only`。

## 成功标准

完成一次 neat 同步必须满足：

- 所有被本次变更影响的知识层，以及没有增量指向的全部存量记忆，都有明确结论：已更新、不需要更新、无法判断。
- 第零步尺寸体检、第一步机械式全量枚举与逐条审查不可跳过；记忆覆盖数量必须对账，未读或未核实项不能判为 `keep`。
- 同作用域 `CLAUDE.md` 与 `AGENTS.md` 内容一致；未解决分歧、无法读取的记忆都必须作为未完成项交付。
- 每个实际改动都能追溯到代码、配置、git diff、用户要求或现有文档冲突。
- 项目级规则文件只保留下次开发必须知道的规则，不承载历史叙事。
- README 和 docs 面向外部读者，包含运行、接入、运维或架构所需的最新信息。
- 记忆层只保存跨会话有复用价值的信息；若当前平台禁止自动写记忆，输出建议文本而不是擅自改。
- 交付时说明改了什么、为什么这样改、如何验证、还有哪些风险。

## 第零步：尺寸体检（所有模式必做）

先确认当前项目根、相关项目和当前环境实际提供的 agent 记忆根目录。按平台配置、已提供路径或索引定位，不猜目录，不遍历整台机器或无关账号。确认目录后，其内部不能再按项目关键词或本次增量筛选。先记录文件总数、每个文件的字节数和行数，再开始内容审查。

| 文件 | 软限制 | 超过后的处理 |
|------|--------|--------------|
| `CLAUDE.md` / `AGENTS.md` | 约 300 行或 15KB | 精简历史叙事和重复指针 |
| `README.md` | 约 500 行 | 拆到 docs，保留入口 |
| 单个 `docs/*.md` | 约 1500 行 | 拆分或增加索引 |
| 记忆索引 | 约 150 行 | 合并重复和过期内容 |

所有记忆文件都计入体检，不只检查索引。尺寸超限不代表过期，也不是跳读理由；大文件分段读完。记录超限项和读取障碍，无法枚举时明确说明覆盖未知，不能声称已完成体检。

## 第一步：机械式全量枚举与存量审查（所有模式必做）

### 1. 枚举并逐个读完记忆文件

对已定位的每一个 agent 记忆根目录，递归列出**每一个文件**，包括隐藏文件、被忽略文件、未被索引引用的孤立文件及子目录文件。可用 `rg --files --hidden --no-ignore <记忆根目录>`，没有 `rg` 时使用平台等价枚举。符号链接单独记录目标与可达性；在获准记忆范围内读取目标并避免循环，范围外目标列为受限项，不擅自扩展读取。

按清单逐文件完整读取，再逐条审查文件内的事实。不能用索引摘要、关键词命中、抽样、mtime、最近更新过或上次已审查代替正文。非文本文件也必须登记，能用适配读取器则检查；不可读项说明原因，不静默跳过。工具输出截断时继续分段读取；上下文不足时保存覆盖进度并续读，不能降低覆盖率。

建立内部覆盖表，清单中一个文件都不能漏：

| 文件 | 大小/行数 | 全文读取状态 | 逐条事实结论与证据 | 待核实项 |
|------|-----------|--------------|--------------------|----------|

覆盖表不复制敏感正文；有几条事实就审几条，不能用文件级 `keep` 掩盖条目缺漏。

### 2. 每条存量记忆的强制检查

- **description 与正文**：检查描述、标题、索引摘要与正文的范围、条件、结论是否一致；无 description 的格式不强加字段。修正文时同步受影响的索引和摘要。
- **绝对时间**：清查“今天、最近、刚刚、上周、目前、当前”等表述。只有来源能确定日期时才换成绝对日期（必要时含时区）；不能把审计日当事件日。时间不明则查证、标未知或提出删除建议。历史原文引用保留时必须明确历史身份与已知时间，不能仍作为当前指令。
- **自然失效**：不论本次是否修改相关代码，逐条核实路径是否存在、残片/备份是否仍保留、待办是否已完成，以及环境、部署、模型等状态是否仍成立。核验必须匹配记忆中的机器、项目、账号和环境；本机不存在不能证明远端已删除。
- **易变快照**：“当前主模型是 X”等不能转成长期默认规则。仅在有复用价值时保留带绝对观测时间、适用环境和“使用前重新核实”的历史快照；否则建议移除。一次观测不能抹掉用户按任务切换模型的事实。
- **记忆间矛盾**：读完全部文件后，按同一实体、属性、环境及有效时间交叉比较，也比较索引与正文、记忆与规则文件。区分历史演进与同时间冲突；不能简单按文件更新时间选赢家。无法判定时列出冲突双方及缺少的证据，询问用户。

`keep` 必须有逐条准确性依据；“最近更新过”“这次没改到”都不是依据。缺乏当前核验能力时标为待核实，不能当作仍有效。

### 3. 对账后才能收窄项目 docs

结束前重新枚举，用路径集合及读取前后的内容指纹（或等价内容比对）核对新增、删除或变动文件并补审，不能只比较文件总数；指纹仅用于发现审查期间变化，不能替代逐条事实核验。报告枚举总数、完整读取数、完成逐条审查数、受限/未核实项；数量不闭合或存在未完成项时，不得宣布全量审查通过。确认当前环境没有记忆系统时记为“不适用”，不要与“目录不可访问”混淆。

随后检查 `git status --short`、`git diff --stat`，枚举项目 README、docs 及同作用域规则文件。**范围收窄只允许减少项目级 docs 的扫描深度，不能减少记忆层存量逐条审查，也不能跳过规则文件配对比对。**没有新变更指向的自然失效知识同样进入证据账本。

读取范围始终服从用户明确边界和上级规则；若其限制全量读取，只能做部分审计并报告缺口，不能绕过限制或宣称完整。是否允许写记忆不影响允许范围内的只读审查。

## 第二阶段：证据账本

在改文件前建立内部证据账本，同时接收“本次增量”和“存量逐条审查”两路发现。每条候选同步事项都要有证据，不凭记忆猜。

```markdown
## 证据账本
| 事实或冲突 | 证据来源 | 影响层 | 动作 | 验证方式 |
|------------|----------|--------|------|----------|
```

动作只能是：

- `update`：现有内容过期或缺失，应该修改。
- `keep`：内容仍准确，不需要改。
- `remove`：内容是历史叙事、重复或已废弃。
- `ask`：证据不足，必须让用户决定。
- `defer`：暂不能处理的事项，记录原因与下一步；不得以没有增量指向为由跳过存量记忆审查，也不能计为已核实。

影响层参考 `references/change-impact-matrix.md`。不确定时先查矩阵。

## 第三阶段：最小同步

编辑顺序：

1. 先改面向人的文档：`README.md`、`docs/`。
2. 再改项目级 agent 指令：`CLAUDE.md`、`AGENTS.md`。
3. 最后处理记忆层或输出记忆建议。

### README 和 docs

README 负责让读者快速判断项目是什么、怎么安装、怎么运行、从哪里深入。细节放到 docs。

docs 负责解释外部接入、架构、运维、排障和交接。新增能力通常检查四类文档：

- 使用入口：README、quick start、usage。
- 接入方式：integration guide、API 示例、配置项。
- 内部机制：architecture、data flow、状态机。
- 运维交接：runbook、handoff、CHANGELOG。

### CLAUDE.md 和 AGENTS.md

项目级 agent 文件是规则手册，不是变更日志。只放下次 agent 写代码时必须看到的信息：

- 项目结构、边界、禁区。
- 常用命令和验证方式。
- 环境变量、外部服务、权限模型。
- 容易反复踩坑的规则。
- docs 指针表，但不要重复粘贴 docs 全文。

不要添加"某日期完成了某功能"这类历史叙事；它属于 git log、CHANGELOG 或 handoff。

**跨工具一致性是强制验收项：**

- 按目录作用域配对读取 `CLAUDE.md` 与 `AGENTS.md`，同时识别实际存在的大小写变体以及用户所称的 `agent.md`（标准文件名是 `AGENTS.md`）。不要在大小写不敏感的文件系统上制造重复文件，不把父目录与子目录的不同规则混为一对。
- 同作用域默认保持全文内容一致，不能只同步本次改动段落，也不能仅留“见另一个文件”的指针。平台专属说明可以明确标注适用工具后同时写入两份，方便 Codex、Claude Code、zcode 等环境切换。
- 单侧缺失时，写入模式下依据已核实内容补齐标准配对文件；只读模式只报告缺失。现有别名应核实使用关系并同步，不能擅自删除或改名。
- 分歧先用代码、配置和用户已确认决策裁定；互不冲突的规则保留并合并到两份。无法裁定则提出一个具体问题，展示冲突条目及后果，不按工具偏好、文件名或 mtime 选赢家，不覆盖用户尚未确认的规则。
- 除非用户明确要求保留差异，否则同步后做全文 diff，差异应为零；明确授权的差异单列理由和范围。远端机器或其他 checkout 不可访问时仅报告本地验证，不声称跨机器已经同步。

### 记忆层

先遵守当前 agent 的上级规则。若平台允许写记忆，并且用户明确要求更新记忆，才写入。否则输出"建议写入记忆"的小节，内容控制在一条事实一段，包含适用范围、事实、使用条件。

记忆适合保存：

- 用户长期偏好。
- 跨项目稳定约定。
- 非显而易见、下次很可能复用的项目事实。
- 已验证的坑点和避免方式。

记忆不适合保存：

- 单次流水账。
- 已完成待办。
- 过期中间态。
- docs 已经清楚描述的细节全文。

## 第四阶段：反膨胀规则

每次修改都先问：

1. 这条信息是否还有读者？
2. 读者会在什么时候需要它？
3. 如果删掉，下次开发会不会犯错？
4. 是否已经有更权威的位置记录？

若答案指向"不会犯错"或"别处更权威"，优先删除、合并或迁移。

常见处理：

| 问题 | 处理 |
|------|------|
| 顶部连续 blockquote 记录历史 | 删除或迁到 CHANGELOG |
| 多处写同一命令且不一致 | 保留一处权威入口，其他地方链接 |
| docs 里有相对时间 | 改成绝对日期或删除时间 |
| CLAUDE.md 复制 architecture 细节 | 改为一行规则或指针 |
| README 堆满内部实现 | 迁到 docs，README 留摘要 |

## 第五阶段：验证

根据改动类型选择最小验证：

- Markdown 结构：确认引用文件存在、链接相对路径合理。
- 文档事实：用 `rg` 搜代码、配置或 docs，确认路径、命令、环境变量、API 名称存在。
- Git 变更：用 `git diff --check` 检查空白错误，用 `git diff --stat` 确认改动范围。
- 脚本或命令：如果文档新增了命令，能安全运行时跑 `--help`、`doctor` 或最小测试。
- 记忆覆盖：复核覆盖表数量、逐条结论、description/正文一致性、时间、自然失效和跨文件矛盾；未完成项不能宣称通过。
- 规则一致性：同作用域配对文件全文 diff 为零，或仅有用户明确授权且列明的差异；缺失/冲突如未解决则验收未完成。
- 记忆建议：检查没有无锚点相对时间、没有敏感信息、没有单次流水账；区分已应用与待写入建议。

验证失败时先修复；无法验证时在交付里直说原因。

## 第六阶段：交付格式

交付必须简洁；无论模式，都包含记忆覆盖计数、待核实项及规则文件配对结果。存在未完成项时把“同步完成”改为“部分同步，审查未完成”。按以下结构：

```markdown
## 同步完成

### 修改了什么
- `<文件>`：一句话说明改动。

### 为什么这样改
- 说明核心依据，引用代码、配置、现有文档冲突或用户要求。

### 如何验证
- 列出实际运行的命令和结果。

### 风险或未验证项
- 没有就写"未发现明显未验证风险"。
```

如果是 `audit-only`，改为：

```markdown
## 审计结果

### 必须处理
### 建议处理
### 不需要处理
### 证据
```

## 错误处理

- 找不到项目根：停止并询问用户目标路径。
- 文档和代码冲突但无法判断真相：列为 `ask`，不要猜。
- 发现用户未提交改动：不要回滚，不要覆盖；只在相关文件上谨慎合并。
- 需要删除文件：只删除明显由本次同步产生且不需要的文件；历史文件删除前要有证据，风险高时先确认。
- 跨项目影响不清楚：先更新当前项目，并把下游风险列为未处理。
- 当前平台不支持写记忆：输出建议，不使用旁路工具强行写。
