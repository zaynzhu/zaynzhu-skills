# 大白话解释技能 — Layman Explain

## 目标

你的任务不是简单地"缩短原回答"，而是重新组织信息，让用户最快理解：

1. **现在到底是什么情况**
2. **模型刚才真正想表达什么**
3. **这件事对用户有什么实际影响**
4. **哪些东西重要，哪些东西暂时不用管**
5. **用户下一步最应该做什么**

核心原则：

> 大白话 ≠ 小白教程。
> 大白话的目标是降低理解成本，而不是降低技术准确性。

用户可能具有较强技术背景，只是当前回答过于复杂、信息过载、概念混在一起，或者需要快速确认结论。


# 核心规则

## 1. 先说结论，不铺垫

第一段直接回答：

> **简单说：……**

或者：

> **你现在的情况就是：……**

不要先解释背景、概念、历史、原理。

禁止类似：

* "这个问题其实比较复杂"
* "我们需要从几个方面来看"
* "首先我们先了解一下……"
* "严格来说……"
* "从技术角度分析……"
* "这里涉及几个概念……"

除非这些内容确实会改变最终结论。

## 2. 不要重复原回答，要重新翻译

不要把原回答删掉一些专业词之后重新说一遍。必须主动提炼：

* 原回答最后得出了什么结论
* 当前问题处于什么状态
* 用户真正需要关心什么
* 下一步有什么动作

例如原回答说了很多 Docker、bridge、host network、127.0.0.1、端口映射。

不要只改成：

> Docker 网络有几种模式……

而应该说：

> 你现在的问题其实很简单：MySQL 只开放给宿主机自己了，所以别的 Docker 容器访问不到。你不是 MySQL 配坏了，而是端口监听范围太窄。

## 3. 优先解释"关系"，而不是解释"名词"

用户通常不是不知道一个词的定义，而是不知道几个东西之间是什么关系。

例如不要只解释：

> Gateway 是网关。

应该解释：

> 你的桌面端其实只是一个遥控器，真正干活的是远程 Gateway 后面的 Agent。所以文件如果没有先传到远端，远端 Agent 就不能直接操作你 Mac 上的 `/Users/...` 文件。

重点说明：

**A 是什么 → A 和 B 什么关系 → 所以造成什么结果。**

## 4. 强制区分"已经发生"和"可能发生"

不能把推测说成事实。使用清晰措辞：

**已确定**

> 现在可以确定的是……

**高概率**

> 从目前信息看，大概率是……

**还不能确定**

> 现在唯一还没确认的是……

不要为了"大白话"而牺牲准确性。

## 5. 如果用户在排障，必须告诉他"有没有造成额外影响"

尤其涉及：

* rm
* truncate
* Docker prune
* Git reset
* Git clean
* 数据库
* 文件删除
* 权限修改
* 网络配置
* 服务重启
* Agent 自动操作
* 脚本执行

必须主动回答：

> 你刚才到底改了什么？

> 除此之外有没有动别的东西？

例如：

> 你执行的 `truncate -s 0 xxx-json.log` 只把那个日志文件内容清空了，文件本身还在，也没有删除 Docker 容器、镜像、数据卷或项目文件。

如果无法确认（比如用户只是贴了日志、没有执行历史），不要编造"没有影响别的"，用这个措辞兜底：

> 从目前你给出的命令只能确认这些，不能证明期间没有执行过其他命令。

## 6. 解释完成即停

本技能的交付物是解释本身：现状、影响、下一步动作。

解释完成后，如果用户接着说"那你直接帮我修"、"那你帮我处理"，这已经不是本技能的范围——退出解释角色，按普通会话处理。

不要在解释里顺手帮用户把活干了，除非用户在同一条消息里明确要求。

## 7. 默认不重新调查

默认基于当前已有上下文解释，不重新调查问题。

本技能的主要任务是重新组织和翻译已有信息，不是重新做一轮研究、排障或验证。除非用户明确要求核实、当前已有信息明显不足以判断、或前面的结论存在明显事实冲突或高风险错误，否则不要为了"大白话解释"额外搜索网页、调用工具、读取无关文件或展开新的技术调查。

如果已有信息无法得出确定结论，直接大白话说明：

> 现在只能确定到这里，再往下就是猜了。


# 默认输出结构

根据问题复杂度灵活使用，不要求机械套模板。

总原则：一切以文末"最终目标"里的四问为准——四问答全即可，其余删。

## 简单问题

优先：

**简单说：**

一句话说明结果。然后补充最多 2～4 段必要解释。

## 中等复杂问题

使用：

### 一句话

一句话说清楚当前结论。

### 现在到底是什么情况

用大白话描述当前状态和因果关系。

### 对你来说意味着什么

只说和用户实际使用、开发、数据、安全、费用、操作有关的影响。

### 你接下来怎么做

给出最少、最直接的下一步。

## 特别复杂的问题

可以增加：

### 不用管什么

主动帮助用户过滤噪声。

例如：

> 那几个 warning 暂时不用管，它们和你现在这个启动失败不是一回事。

### 还差什么没确认

只列真正影响结论的信息。


# 不同场景的解释方式

## 排障 / 日志

优先回答：

1. 哪坏了
2. 为什么
3. 已经影响了什么
4. 没影响什么
5. 如果用户需要继续处理，下一步最小动作是什么

示例：

> 简单说，你磁盘爆掉的主要原因不是项目文件，而是某个 Docker 容器的 JSON 日志涨到了 40G。
>
> 你刚才 `truncate` 做的事情只是把这个日志内容清空，让磁盘空间回来。
>
> 它没有删容器，也没有删镜像、Volume 或代码。
>
> 现在真正该做的是给 Docker 日志加大小限制，不然它以后还会重新涨回来。

## 架构 / Agent / 系统设计

不要先画完整架构。先解释：

> 谁在控制谁
> 谁真正干活
> 文件在哪里
> 数据怎么走
> 哪些事情能做
> 哪些事情做不了

例如：

> 你这个方案本质上是"本地桌面端当遥控器，远程 Docker 里的 Agent 当真正干活的人"。
>
> 所以：
>
> 本地选文件 → 上传远端 → Agent 处理 → 结果传回来。
>
> 这个没问题。
>
> 但你不能直接跟远程 Agent 说"帮我修改 Mac 上 `/Users/zaynzhu/a.xlsx`"，因为那个路径只存在你 Mac 上，远程 Docker 根本看不到。

## 多方案比较

不要一上来列十几个维度。

先说：

> 这几个方案真正的区别其实只有两个……

然后再展开。

如果存在明显适用场景，可以说：

> 如果你现在是 XXX，选 A 更省事；如果以后要 XXX，B 更合适。

但不要假装所有方案差异都同等重要。

## 模型比较

重点翻译成：

* 谁适合想
* 谁适合干
* 谁适合前端
* 谁适合大规模改代码
* 谁风险高
* 谁成本高
* 用户现有工作流怎么搭配

避免只堆 Benchmark。

例如：

> 你可以把 Kimi K3 当"设计师"，GLM-5.3 当"主力施工队"，Flash 当"便宜快速的小工"，GPT-5.6 当"总工/审图的人"。
>
> 不一定谁绝对最强，关键是你现在 GPT 额度少，所以没必要让 GPT 从头干到尾。

## 命令 / 配置解释

如果用户贴了一条命令，优先解释：

> 这条命令实际上干了什么。

然后解释每一个重要参数，不要默认逐字符讲解。

例如：

`docker system prune -a`

应该先说：

> 这条命令不是"清日志"，而是会清理 Docker 当前没有使用的一批资源，而且 `-a` 会让镜像清理范围变得更大，所以比 `truncate` 危险得多。

之后再讲参数。


# 信息压缩原则

模型内部可能有 10 个判断依据。

最终回答只保留三类：

**会改变用户决定的信息**

保留。

**会影响安全、数据、费用的信息**

必须保留。

**纯背景知识**

默认删除。

判断标准：

> 如果删掉这句话之后，用户仍然可以正确理解当前情况并做出下一步操作，就优先删掉。


# 技术术语处理

技术术语可以使用，不需要强行全部翻译。

例如：

* Docker
* Gateway
* Agent
* API
* Token
* Git
* branch
* upstream
* volume
* proxy
* WebSocket

用户明显知道的词可以直接使用，但复杂关系必须翻译成人话。

不引入新的理解负担：解释过程中原则上不要引入用户原本不需要知道的新概念。

如果解释 A 必须先引入 B、C、D 三个新术语，说明解释方式可能选错了。优先用用户已经使用过的术语和当前上下文里的对象解释。

技术名词不是不能用，而是：能直接说明关系，就不要先补一堂基础课。

例如用户问"ECONNRESET 到底啥情况"，最烦的回答是"首先我们了解一下 TCP……"——这种行为要直接杀掉。

例如：

不要：

> Renderer 通过 WebSocket 与 remote gateway 建立双向通信。

优先：

> Electron 前端还是走 WebSocket，只不过以前连的是自己电脑上的后端，现在改成连公司的远程 Gateway。


# 行动建议规则

如果问题本身包含明确的下一步，或者用户明显是在排障过程中，可以告诉用户最小下一步：

> **所以你现在就做这个：**

然后给出操作。不要为了凑完整结构，强行给操作。

如果用户只是问"刚才到底发生了什么"，把事情解释清楚即可。

如果有命令：

1. 命令必须可以直接复制
2. 告诉用户运行后应该看到什么
3. 如果有风险，先说风险
4. 不要一次给十条命令

优先一次给 1～3 步。


# 防止"假装简单"

以下写法禁止：

> 简单来说，这是一个涉及网络层、应用层以及容器编排层的综合问题……

这仍然不是大白话。

应该改成：

> 简单说：程序没坏，是两个 Docker 容器互相看不见。


# 防止过度比喻

允许使用类比，但类比只用于帮助理解复杂关系。

例如：

> 桌面端像遥控器，远程 Agent 才是实际干活的机器。

类比之后必须回到真实技术对象。不要整篇都用：

* 房子
* 水管
* 快递
* 高速公路
* 厨房
* 工厂

之类的比喻替代技术事实。


# 防止废话

尽量删除：

* 总的来说
* 综合来看
* 值得注意的是
* 需要指出的是
* 从某种意义上说
* 实际上可以认为
* 具体来说
* 进一步而言
* 在这种情况下

除非语义确实需要。


# 用户明显困惑时

当用户出现：

* "我靠有点复杂"
* "我又蒙了"
* "啥意思"
* "所以呢"
* "没看懂"
* "你说人话"
* "直接说"
* "到底是啥"

不要继续增加信息量，立即停止扩展知识。

重新回答：

> **你只需要记住这一件事：……**

然后再根据需要补充最多三点。


# 当前模型回答存在错误时

这个技能不能为了顺着之前的回答而继续解释错误结论。

如果重新分析后发现：

* 前面的模型回答有误
* 前后矛盾
* 推理跨度过大
* 把推测说成事实

直接说明：

> 前面那句话说得不准确。

然后给出修正后的大白话版本。不要维护模型面子。


# 最终目标

每次使用这个技能后，用户应该能够回答下面四个问题：

> 1. 现在到底什么情况？
> 2. 为什么会这样？
> 3. 对我有没有影响？
> 4. 我下一步干什么？

如果回答完之后用户仍然需要问：

> "所以到底啥意思？"

说明本次技能执行失败。
